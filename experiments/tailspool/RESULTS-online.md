# 持续打流时的进程恢复与检查点

单台 10.98.1.5，OTLP/gRPC，24,576 span/s，每批 128 个 span，ERROR 策略，30 秒决策窗口，backend cgroup 限额 512 MiB，禁用 swap，GOMEMLIMIT 320 MiB。沿用 v0.165.1 加两项 TakeMany 回移。每轮打流 155 秒，约第 77 秒在已有检查点时向正在处理请求的 backend 发送 SIGKILL。systemd 配置自动重启延迟 50 ms，单个 gRPC 客户端连接的重连退避为 20 ms。发生器保持调度，每个批次只发送一次，记录 ID、调用起止时间和结果。使用完整 span 内容连同 Resource、Scope 及 schema URL 的摘要多重集合校验。

## 接入与恢复路径

进程先开放 gRPC。元数据回放期间，新批次写入独立文件，原文写完、文件改名后即可 ACK。接管时用硬链接将同一 inode 纳入原文段，WAL 先记录来源 ID 再解除临时文件名。单测覆盖在此交接中途再次崩溃的情况。

注册日志持久化绝对到期时间。历史待决 trace 使用首个关联批次的到期时间。恢复期间同一 trace 的新 span 在到期前可补充 ERROR 状态；到期后先确定旧决策，再处理迟到批次。恢复路径按当前固定 ERROR 谓词求值，普通新 trace 继续使用官方 sampler。历史决定调度和新接收并行。旧格式日志缺少时间戳，首次升级恢复时只能使用新的等待窗口。

检查点保存活动记录的原文位置、未决引用和 ERROR 标记、已知 keep、两个有界决策缓存的顺序、最后提交的导出位置和序列号。写完快照并同步后，以原子 rename 替换 WAL，新的增量继续追加。实验使用新增元数据 8 MiB 触发一次，默认值为 16 MiB。快照本身的大小取决于待决工作集。生成检查点时持有 spool 锁，可能短时增加接收延迟。

## 计量口径

接入空窗取 kill 前后两秒内客户端相邻成功响应间的最大间隔，另记录 kill 至新进程启动后发起的首个成功请求返回的耗时。这样可以排除旧连接的在途 ACK。每批的期望 hash 根据发送 ID 与固定输入规则独立生成。ACK 清单必须匹配且重数相同。对于报错请求，单独核对是否可能在连接中断前已被接收。测试包括本地校验 sink；主机掉电、LB 重试和 Kafka 提交语义不在此次故障注入范围内。

最终构建中，kill 前 30 秒、kill 后首个 30 秒、kill 后第 35 至 65 秒的 ACK 吞吐分别为 24,576、24,329、24,585 span/s。排除 kill 前后两秒后，成功 RPC 延迟中位数 1.69 ms、P99 为 106.87 ms。这项口径包含正常写盘、决策、锁等待和检查点。复测中四次检查点发布后的相邻采样文件大小为 5.1 至 5.7 MiB，最后一次从约 13.7 MiB 收缩至 5.7 MiB。排空时 WAL 含后续增量，共 13.85 MiB。

复测中 58 个批次共 7,424 个 span 未获 ACK。无重试的单 backend 链路仍存在实际接入失败。完整测量与清单摘要见 [JSON](benchmark-results-online.json)。测试机目录为 `/data/otel-tail-bench/online-deadline-confirm`，其中 `outcomes.csv` 保存所有调用结果，`backend/actual.sha256` 保存实际逐 span 摘要。
